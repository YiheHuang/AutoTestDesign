# 详细测试设计与执行文档

项目名称：Task Management Platform  
选定模块：任务管理模块（REQ-005、REQ-006、REQ-007）

## 1. 测试对象

本次详细测试选择任务管理模块作为重点对象，覆盖以下 3 条需求。

| 需求 | 内容 | 风险等级 | 测试优先级 |
|------|------|----------|------------|
| REQ-005 | 任务管理 | Medium | Medium |
| REQ-006 | 任务分配 | Medium | Medium |
| REQ-007 | 任务统计 | Low | Low |

选择该模块的主要原因有两点。第一，该模块同时包含创建、更新、删除、分配、统计等多类行为，适合同时展示黑盒和白盒测试。第二，该模块存在若干已知需求偏差，便于观察自动化测试设计工具在真实场景中的有效性与局限。

## 2. 测试设计思路

本轮测试首先通过 AutoTestDesign 读取标准需求、需求-代码映射与风险分析结果，再针对 REQ-005 到 REQ-007 生成黑盒和白盒测试资产。随后保留原始自动导出的脚本，并进一步整理出人工校验后的自动脚本以及一份人工编写的对照脚本，用于比较三者差异。

### 2.1 黑盒测试设计

黑盒部分采用等价类划分、边界值分析和判定表 3 种技术。

#### 等价类划分

等价类划分主要用于任务标题、优先级、状态和负责人字段。

| 字段 | 有效类 | 无效类 |
|------|--------|--------|
| `title` | 非空、长度在允许范围内 | 空、超长 |
| `priority` | Low / Medium / High | 非法枚举 |
| `status` | todo / in_progress / done | 非法枚举 |
| `assignee` | 合法负责人输入 | 空值、未注册用户 |

#### 边界值分析

边界值分析主要围绕 `title` 长度和日期输入展开。

| 检查点 | 代表值 |
|--------|--------|
| 最小长度附近 | 1、2 |
| 最大长度附近 | 199、200、201 |
| 日期边界 | 过去日期 |

#### 判定表

判定表主要用于任务创建、任务分配和任务统计的条件组合。

| 需求 | 典型条件 |
|------|----------|
| REQ-005 | 项目是否存在、优先级是否合法 |
| REQ-006 | 负责人输入是否存在、是否满足分配条件 |
| REQ-007 | 项目是否存在、统计请求是否有效 |

### 2.2 白盒测试设计

白盒部分采用路径覆盖和状态转换两种技术。

#### 路径覆盖

路径覆盖主要针对以下代码路径。

| 路径 | 关注点 |
|------|--------|
| 任务创建路径 | 项目不存在、标题非法、创建成功 |
| 任务更新路径 | 任务不存在、更新成功、非法输入 |
| 任务删除路径 | 删除成功、删除已完成任务 |
| 任务详情路径 | 任务存在 / 不存在 |

#### 状态转换

状态转换主要围绕任务生命周期建模，例如创建任务、查看任务、更新任务、删除任务和查询统计等流程。这种设计方式可以覆盖单纯字段校验之外的过程行为。

## 3. 测试脚本组织

本轮共保留 3 份测试脚本。

| 文件 | 作用 |
|------|------|
| `test_scripts/test_generated.py` | 原始自动导出脚本 |
| `test_scripts/test_generated_refined.py` | 人工校验后的自动脚本 |
| `test_scripts/test_human.py` | 人工编写的对照脚本 |

其中，后两份脚本都保持了与原始自动脚本一致的基本结构，仍然按等价类划分、边界值分析、判定表、路径覆盖、状态转换组织，而不是仅保留零散示例。

从用例规模上看，各脚本的测试函数数量如下。

| 脚本 | 测试函数数 |
|------|------------|
| 原始自动脚本 | 44 |
| 人工校验后的自动脚本 | 32 |
| 人工编写脚本 | 27 |

## 4. 工具实现与执行方式

测试执行统一采用 Pytest 与 Flask `test_client()`。

运行命令如下：

```bash
python -m pytest test_scripts/test_generated.py -v --tb=short
python -m pytest test_scripts/test_generated_refined.py -v --tb=short
python -m pytest test_scripts/test_human.py -v --tb=short
```

这种方式具有以下优点：

1. 不依赖额外启动 HTTP 服务；
2. 可以直接在进程内调用 Flask 路由；
3. 便于对比不同脚本版本的执行结果。

## 6. 异常现象解释

### 6.1 REQ-005 路径覆盖率只有 43.8% 的原因

`run_results/REQ005_006_007/REQ-005路径覆盖.png` 显示：

- 关联行：73
- 覆盖行：32
- 覆盖率：43.8%

同一张图还提示了 2 个“代码段未覆盖”：

1. 项目任务列表接口，对应 `project_tasks_list()`
2. 单个任务详情接口，对应 `task_detail()`

从代码上看，这两个函数确实位于任务路由 `target_app/flask_app/routes/tasks.py` 中，分别是 `project_tasks_list()` 和 `task_detail()`。

而本轮针对 REQ-005 的需求描述，核心仍然是任务 CRUD、标题校验、优先级枚举和状态枚举。在 `data/sample_input/task_platform_reqs.csv` 中，REQ-005 的重点字段是：

- `title`
- `description`
- `priority`
- `status`

条件部分也主要围绕以下内容展开：

- 项目是否存在
- 优先级是否合法

这会带来一个直接后果：LLM 在生成路径覆盖用例时，会优先聚焦创建、更新、删除这些与字段校验和主要业务动作直接相关的路径，而不会优先补全“列表查询”和“详情查询”这类只读路径。

更关键的是，当前工具的覆盖率计算是按行数计算，而不是按“代码段个数”计算。`tool/src/test_design/white_box/path_coverage.py` 中的 `_compute_coverage()` 实现，就是基于“需求-代码图中的所有行”与“测试用例-覆盖代码图中的已覆盖行”求比例。

这意味着：

1. 覆盖率分母是 REQ-005 映射到的全部 73 行；
2. 分子只统计 LLM 显式返回为“已覆盖”的 32 行；
3. 图中“未覆盖代码段”只列出完全没有被覆盖到的代码段。

因此，“只有 2 个未覆盖代码段”并不等价于“其余代码都完全覆盖了”。当前实现里，只要一个较大的代码段里有部分行被覆盖，它就不会再被列为“未覆盖段”，但行级覆盖率仍然会下降。这也是为什么最终结果会是 **43.8%**，而不是仅凭“2 段未覆盖”就能直观看出的更高比例。

综合来看，REQ-005 的 43.8% 主要来自三个因素：

1. 需求侧聚焦创建、更新、删除，弱化了列表与详情路径；
2. 需求-代码图把较大范围的任务路由代码都映射进来了；
3. 覆盖率采用按行统计，而未覆盖提示只展示完全未覆盖段。

因此，这个覆盖率偏低并不表示工具完全失效，而是说明它对 REQ-005 的白盒路径覆盖更偏向核心写操作路径，而不是把所有只读辅助路径也一起覆盖。

### 6.2 REQ-007 黑盒测试中 EP/BVA 没有生成测试用例的原因

从 `run_results/REQ005_006_007` 目录中可以看到，REQ-007 有以下产物：

- `REQ-007判定表.csv`
- `REQ-007状态转换1.csv`
- `REQ-007状态转换2.csv`
- `REQ-007路径覆盖.png`

但没有 REQ-007 的等价类划分表和边界值分析表。这并不是导出遗漏，而是在生成阶段就没有形成有效的 EP/BVA 用例。

原因首先来自需求本身。当前 REQ-007 在 `data/sample_input/task_platform_reqs.csv` 中的定义非常简洁：

- `input_fields` 是空数组；
- `conditions` 是空数组；
- `expected_behaviors` 只有一条“存在 -> 返回统计结果”。

实际运行截图 `REQ-007标准需求生成.png` 也可以看到：

- 输入字段区域为空；
- 关联代码集中在 `project_stats()`；
- 条件与行为基本只有“存在 -> 返回”。

这与 REQ-007 的实际代码结构是一致的。`project_stats()` 本质上是 `target_app/flask_app/routes/projects.py` 中的一个只读统计接口。

其主要逻辑只有两层：

1. `project_id` 对应的项目是否存在；
2. 若存在，则聚合任务数据并返回统计结果。

这类需求非常适合：

- 判定表，因为存在“项目存在 / 不存在”的条件分支；
- 状态转换，因为可以建模为“请求统计 -> 校验项目 -> 返回统计结果”。

但它并不天然适合：

- 等价类划分，因为没有明确的输入字段集合和字段级有效/无效类；
- 边界值分析，因为没有可直接做边界切分的数值范围、长度范围或显式区间。

从工具实现上看，EP 和 BVA 生成器都是把完整的 `requirement_json` 发送给 LLM，然后期待 LLM 返回：

- `equivalence_classes`
- `boundary_analysis`
- `test_cases`

对应实现分别位于 `tool/src/test_design/black_box/equivalence_partition.py` 与 `tool/src/test_design/black_box/boundary_value.py`。

当需求本身没有输入字段、没有范围、没有边界信息时，LLM 往往只能稳定生成判定表或状态模型，而难以给出有意义的 EP/BVA `test_cases`。当前生成器对这种情况的处理是：

- 允许返回空 `test_cases`；
- 记录 warning；
- 页面最终表现为该技术下没有用例产出。

因此，REQ-007 没有生成 EP/BVA 用例，根本原因不是工具报错，而是：

1. 需求本身更像一个“存在性 + 聚合返回”的只读统计需求；
2. 没有明确输入字段、边界范围和字段约束；
3. 判定表和状态转换比 EP/BVA 更适合表达这类需求。

这也说明，当前工具对不同需求类型已经表现出一定的技术适配性。当需求不具备字段边界信息时，工具不会强行产出质量较差的 EP/BVA 用例，而是更容易在判定表和状态转换上产出结果。

## 7. 两类最终测试脚本的对比

为了更直观比较人工校验后的自动脚本与人工脚本，相关关键指标汇总如下。

| 维度 | `test_generated_refined.py` | `test_human.py` |
|------|-----------------------------|-----------------|
| 来源 | 自动生成后人工校验 | 人工从头编写 |
| 测试函数数 | 32 | 27 |
| 脚本本身错误数 | 0 | 0 |
| 真实缺陷发现数 | 3（BUG-7、BUG-8、BUG-9） | 1（BUG-9） |
| 修复/编写时间 | 约 20 分钟校验修正 | 约 4 小时人工设计与编写 |
| LLM 成本 | 输入 79,260 / 输出 10,828，费用约 ¥2 | ¥0 |

通过对比可以得到两点结论。

第一，自动工具的主要价值体现在起点更高。它已经给出了较完整的测试框架和大量候选用例，人工工作更多是在筛选和修正，而不是从零开始构造。

第二，人工脚本并不天然更可靠。虽然它没有依赖自动导出，但同样会出现脚本级错误，而且在缺陷发现能力上明显弱于人工校验后的自动脚本。

## 8. 与已知缺陷的对应关系

任务管理模块相关的已知缺陷为 BUG-7、BUG-8、BUG-9。

| 缺陷 | 含义 | 本轮发现情况 |
|------|------|--------------|
| BUG-7 | 未正确处理未注册负责人的分配或更新场景 | 由 `test_generated_refined.py` 发现 |
| BUG-8 | 已完成任务仍可删除 | 由 `test_generated_refined.py` 发现 |
| BUG-9 | 过去日期的 `due_date` 未被拒绝 | 由 `test_generated_refined.py` 与 `test_human.py` 发现 |

因此，从与已知缺陷记录的贴合度看，人工校验后的自动脚本明显优于人工脚本。

## 9. 结论

本次详细测试设计与执行可以得出以下结论。

1. AutoTestDesign 在测试设计阶段已经表现出明显优势。它能够较快产出黑盒分析表、白盒覆盖思路和大规模候选测试脚本，这一点是纯人工方式难以在短时间内达到的。

2. 自动生成脚本并不能完全跳过人工环节。原始自动导出脚本的问题较多，但经过一次规模不大的人工校验后，脚本质量有明显提升，缺陷发现能力也显著增强。

3. 从本轮实际结果看，更合理的工作方式不是“自动化替代人工”，而是“自动化生成初稿，人工做关键校验”。这一方式在时间成本和缺陷发现能力之间取得了更好的平衡。
