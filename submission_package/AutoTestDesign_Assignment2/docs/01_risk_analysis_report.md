# 风险分析报告

项目名称：Task Management Platform（任务管理平台）

## 1. 项目概述

### 1.1 应用背景

被测应用是一个基于 Flask 和 SQLite 实现的任务管理平台，主要面向小型团队的任务协作场景。系统提供用户认证、项目管理和任务管理 3 个主要模块，采用 RESTful API 形式对外提供服务，后端代码按路由、数据模型和校验逻辑分层组织。

本报告的目的，是在测试活动开始前对目标应用的主要需求进行风险识别和分级，为后续测试计划、测试资源投入和测试技术选择提供依据。

### 1.2 功能范围

| 模块 | 主要功能 | 主要接口 |
|------|----------|----------|
| 用户认证 | 注册、登录、密码重置、登出 | `/api/register`、`/api/login`、`/api/forgot-password`、`/api/reset-password`、`/api/logout` |
| 项目管理 | 项目创建、查询、修改、删除、统计 | `/api/projects`、`/api/projects/<id>`、`/api/projects/<id>/stats` |
| 任务管理 | 任务创建、更新、删除、分配、按用户查询 | `/api/projects/<id>/tasks`、`/api/tasks/<id>`、`/api/tasks/<id>/assign`、`/api/users/<name>/tasks` |

### 1.3 技术背景

| 维度 | 内容 |
|------|------|
| 开发语言 | Python 3.11+ |
| Web 框架 | Flask 3.0 |
| 数据存储 | SQLite |
| 架构方式 | Blueprint 路由拆分 + 工厂模式 |
| 测试执行方式 | Pytest + Flask `test_client()` |

## 2. 风险分析方法

### 2.1 分析思路

本报告采用“需求分解 + 风险评估 + 人工复核”的方式开展风险分析，具体步骤如下：

1. 依据需求文档将系统拆分为 7 条标准需求；
2. 从功能关键性、数据敏感性、安全影响、业务复杂度和用户可见度等维度评估风险；
3. 为每条需求给出风险等级和测试优先级；
4. 结合被测应用的实现方式，补充技术层面的风险判断。

### 2.2 风险等级定义

| 风险等级 | 定义 |
|----------|------|
| High | 涉及认证、安全、敏感数据或核心业务流程，失效后会对系统可用性或安全性造成直接影响 |
| Medium | 涉及主要业务功能，失效会影响用户使用或数据一致性，但不一定立即破坏核心认证能力 |
| Low | 辅助功能或展示类功能，失效后影响范围较小，通常不会阻断核心业务 |

### 2.3 评估维度

| 维度 | 关注点 |
|------|--------|
| 功能关键性 | 是否属于核心业务路径 |
| 数据敏感性 | 是否涉及密码、账户、个人信息 |
| 安全影响 | 是否可能引入认证绕过或非法访问 |
| 业务复杂度 | 是否包含较多条件组合、状态流转或分支判断 |
| 用户可见度 | 问题是否会直接暴露给终端用户 |

## 3. 需求级风险分析

### 3.1 总体结果

| 需求 ID | 功能名称 | 风险分数 | 风险等级 | 测试优先级 | 主要风险因素 |
|---------|----------|----------|----------|------------|--------------|
| REQ-001 | 用户注册 | 90 | High | High | 输入字段多、密码规则复杂、涉及用户唯一性 |
| REQ-002 | 用户登录 | 92 | High | High | 锁定逻辑、失败计数、认证正确性 |
| REQ-003 | 密码重置 | 88 | High | High | Token 时效、密码修改、安全提示一致性 |
| REQ-004 | 项目管理 | 68 | Medium | Medium | 项目删除后的数据完整性、名称校验 |
| REQ-005 | 任务管理 | 64 | Medium | Medium | 任务字段校验、状态与优先级约束、日期处理 |
| REQ-006 | 任务分配 | 66 | Medium | Medium | 用户存在性校验、任务与用户关系维护 |
| REQ-007 | 任务统计 | 35 | Low | Low | 统计结果准确性、只读聚合逻辑 |

### 3.2 各需求分析

#### REQ-001 用户注册

该需求包含用户名、密码、确认密码、邮箱和年龄等多个输入字段，涉及格式校验、边界处理和数据库唯一性检查。其结果直接影响账户创建过程，是用户进入系统的第一道入口，因此风险等级确定为 High。

主要风险包括：

- 弱密码被错误放行；
- 用户名或邮箱重复时未能正确拦截；
- 年龄边界值处理不一致；
- 校验顺序不稳定导致返回结果不一致。

建议测试重点为等价类划分、边界值分析和条件组合测试。

#### REQ-002 用户登录

登录功能不仅涉及用户名和密码比对，还包含失败次数统计和账户锁定逻辑。由于其直接影响用户身份认证过程，且带有明显状态变化，因此属于高风险需求。

主要风险包括：

- 连续失败次数统计错误；
- 登录成功后未正确清理失败记录；
- 锁定时长计算错误；
- 账户锁定与解锁条件不稳定。

建议测试重点为判定表、状态转换和边界值分析。

#### REQ-003 密码重置

密码重置功能关系到账户恢复与二次认证安全，包含 Token 生成、过期校验、新密码约束等内容。该功能一旦实现不当，既可能导致合法用户无法恢复账户，也可能带来明显安全风险，因此风险等级为 High。

主要风险包括：

- Token 过期时间计算错误；
- 无效或已过期 Token 未被正确识别；
- 新密码校验不充分；
- 提示信息暴露账户状态。

建议测试重点为 Token 状态覆盖、时间边界测试和安全一致性验证。

#### REQ-004 项目管理

项目管理功能包括项目创建、修改、删除与统计，是任务管理的上层容器。虽然不涉及账户安全，但项目删除后的数据一致性和名称合法性会影响后续任务操作，因此风险等级为 Medium。

主要风险包括：

- 删除项目后仍保留孤立任务；
- 项目名称为空、过长或重复时处理不当；
- 项目不存在时接口返回不一致。

建议测试重点为边界值分析、集成测试和删除后数据一致性验证。

#### REQ-005 任务管理

任务管理需求覆盖任务创建、更新、删除、查看等核心操作，包含标题、优先级、状态、截止日期等多个业务字段。本项目将其风险等级定为 Medium，而不是 Low，原因在于该功能是日常操作频率最高的业务模块之一，并且内部约束较多。

主要风险包括：

- 非法优先级或状态值被错误接受；
- 截止日期校验不完整；
- 项目不存在时仍允许创建任务；
- 已完成任务的处理规则不符合需求。

建议测试重点为等价类划分、边界值分析、判定表以及路径覆盖。

#### REQ-006 任务分配

任务分配涉及任务对象与用户对象之间的关联，是任务协作功能中的关键环节。该需求需要保证负责人输入与用户信息之间的一致性，因此风险等级定为 Medium。

主要风险包括：

- 不存在的负责人被错误接受；
- 分配完成后查询接口未正确反映结果；
- 更新任务时对负责人字段缺少约束。

建议测试重点为等价类划分、判定表和状态转换。

#### REQ-007 任务统计

任务统计功能以只读查询为主，业务复杂度和输入复杂度相对较低，但仍需要保证聚合范围和统计结果的准确性，因此风险等级定为 Low。

主要风险包括：

- 统计范围错误，跨项目混入无关任务；
- 统计口径不一致；
- 项目不存在时未正确返回错误信息。

建议测试重点为判定表、路径覆盖和数据驱动测试。

## 4. 技术风险分析

### 4.1 安全风险

| 风险项 | 等级 | 说明 |
|--------|------|------|
| 密码哈希强度有限 | High | 当前实现使用 SHA-256，缺少更强的专用密码哈希机制 |
| 登录失败记录处理不稳定 | High | 登录与锁定逻辑存在状态依赖，容易出现误锁定 |
| 密码重置时效控制 | High | Token 过期判断与时间处理关系到账户安全 |

### 4.2 数据一致性风险

| 风险项 | 等级 | 说明 |
|--------|------|------|
| 项目删除后的级联处理 | Medium | 若任务未同步删除，容易产生孤立数据 |
| 任务分配对象校验不足 | Medium | 可能出现任务指向不存在用户的情况 |
| 统计范围不准确 | Low | 聚合查询若缺少过滤条件，会导致结果偏差 |

### 4.3 可测试性风险

| 风险项 | 等级 | 说明 |
|--------|------|------|
| 需求描述与实现粒度不一致 | Medium | 某些需求较概括，测试设计时需要补充分支信息 |
| 只读统计需求不适合所有黑盒技术 | Low | 对于输入字段较少的需求，EP/BVA 产出可能有限 |
| 白盒覆盖率依赖需求-代码映射精度 | Medium | 需求映射范围较大时，覆盖率结果容易偏低 |

## 5. 风险对应的测试安排

### 5.1 测试优先级分配

| 优先级 | 对应需求 | 测试安排 |
|--------|----------|----------|
| 高 | REQ-001、REQ-002、REQ-003 | 优先执行，采用多种黑盒与白盒方法交叉验证 |
| 中 | REQ-004、REQ-005、REQ-006 | 结合输入校验与关键路径测试，覆盖主要业务规则 |
| 低 | REQ-007 | 以统计正确性和异常路径为主，保证基本行为可验证 |

### 5.2 测试资源投入建议

1. 认证模块作为高风险区域，应优先完成完整的黑盒测试设计；
2. 任务管理模块作为本次详细测试对象，应同时使用黑盒和白盒方法；
3. 统计类需求可适度减少字段级黑盒设计，转而强调判定表和路径验证；
4. 对已知存在需求偏差风险的模块，应保留人工校验环节。

## 6. 结论

从整体风险分布看，用户认证模块是本项目的最高风险区域，应当作为测试投入的首要重点；项目管理与任务分配次之，重点关注数据一致性和对象关联；任务统计虽然风险较低，但仍需验证聚合逻辑是否正确。

本报告的分析结果为后续测试计划和详细测试设计提供了依据。后续文档中的测试范围、测试技术选择和执行重点，均与本报告中的风险等级和测试优先级保持一致。
