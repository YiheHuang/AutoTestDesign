## 2. 项目范围

### 2.1 背景

Task Management Platform（任务管理平台）是一个基于 Flask + SQLite 的轻量级任务协作系统，提供用户认证、项目管理和任务追踪三大核心功能。系统采用 RESTful API 架构，面向中小团队的任务管理场景。

本项目使用自研的 AI 驱动自动化测试设计工具 (AutoTestDesign v2.2)，对目标应用进行系统化的软件测试，验证工具的泛化能力和测试设计质量。

### 2.2 测试目标

| 目标 | 描述 |
|------|------|
| **功能验证** | 验证 7 条核心需求的功能正确性，覆盖正常路径和异常路径 |
| **风险覆盖** | 优先覆盖 High 风险模块（用户认证），确保安全关键路径 100% 测试 |
| **缺陷发现** | 利用工具自动生成的测试用例，发现系统中的已知缺陷和潜在缺陷 |
| **覆盖率度量** | 通过黑盒（EP/BVA/DT）和白盒（路径覆盖、状态转换）多维度度量测试覆盖率 |
| **效率验证** | 对比 AI 自动化测试设计与手工测试的成本和效率 |

### 2.3 测试范围

**包含范围**:
- 7 条功能需求 (REQ-001 ~ REQ-007)
- 3 个功能模块（用户管理、项目管理、任务管理）
- API 层面的功能测试和集成测试

**不包含范围**:
- 前端 UI 测试（系统为纯 API 服务）
- 性能压力测试
- 安全渗透测试
- 生产环境部署测试

## 4. 高级测试套件设计

### 4.1 基于风险的测试策略

| Medium | REQ-004, 006 | 25% | 80% 需求覆盖 |

### 4.2 测试套件设计

#### 黑盒测试套件 (Black-Box)

| 测试套件 | 关联需求 | 技术组合 | 预期用例数 |
|---------|---------|---------|-----------|
| TS-BB-001 | REQ-001 (用户注册) | EP + BVA + DT | 30-50 |
| TS-BB-002 | REQ-002 (用户登录) | EP + DT | 15-25 |
| TS-BB-003 | REQ-003 (密码重置) | EP + BVA + DT | 20-35 |
| TS-BB-004 | REQ-004 (项目管理) | EP + BVA | 10-20 |
| TS-BB-005 | REQ-005 (任务管理) | EP + DT | 15-25 |
| TS-BB-006 | REQ-006 (任务分配) | EP | 8-12 |
| TS-BB-007 | REQ-007 (任务统计) | EP | 5-8 |

**技术选择理由**:

| 技术 | 适用场景 | 选用的套件 |
|------|---------|-----------|
| 等价类划分 (EP) | 所有涉及输入字段验证的功能 | 全部 7 个套件 |

| 判定表 (DT) | 有条件逻辑组合 (密码正确/错误 × 锁定/未锁定) | TS-BB-001, 002, 003, 005 |

#### 白盒测试套件 (White-Box)

| 测试套件 | 关联需求 | 技术 | 覆盖目标 |
|---------|---------|------|---------|
| TS-WB-001 | REQ-001 (注册) | 路径覆盖 + 状态转换 | validate_* 函数的所有 return 路径 |
| TS-WB-002 | REQ-002 (登录) | 路径覆盖 + 状态转换 | 未登录→登录中→已登录→已锁定 状态全覆盖 |
| TS-WB-003 | REQ-003 (密码重置) | 路径覆盖 | token 验证 + 密码更新路径 |
| TS-WB-004 | REQ-004 (项目管理) | 路径覆盖 | CRUD 操作路径 + 级联删除 |

**技术选择理由**:

| 技术 | 适用场景 |
|------|---------|
| 路径覆盖 | 验证每个函数的所有执行路径（每个 return 语句至少一个用例） |
| 状态转换 | 适用于有明确状态机的功能（登录锁定/解锁流程） |

## 5. 进度安排与检查清单

### 5.1 AI 辅助测试流程

采用双人协作模式：**生成员** 操作 AutoTestDesign 工具生成测试套件，**校验员** 审查用例质量并确认结果。

| 阶段 | 时间 | 生成员 | 校验员 | 产出 |
|------|------|--------|--------|------|
| **P1: 测试准备** | 第 1 天 | 导入CSV/TXT需求 + 加载代码仓库 + 执行风险分析 | 复核标准需求-代码映射准确性 + 风险等级合理性 | 7条标准需求 + 需求-代码图 + 风险矩阵 |
| **P2: 黑盒测试** | 第 2-3 天 | 逐需求生成 EP/BVA/DT 用例 (7套件) | 逐套件审查分析表(等价类/边界值/判定表) + 测试用例合理性 | 7个黑盒套件 + 审查记录 |
| **P3: 白盒测试** | 第 4 天 | 生成路径覆盖 + 状态转换用例 (4套件) | 审查路径覆盖完整性 + 状态机模型正确性 + 覆盖率达标 | 4个白盒套件 + 覆盖率报告 |
| **P4: 预言生成** | 第 5 天 | 针对已知缺陷创建自定义用例 | 验证预期结果与需求的一致性 | 自定义测试套件 |
| **P5: 套件优化** | 第 5 天 | 执行风险优先级排序 + 覆盖最小化 | 确认优化后覆盖率不低于目标值 | 优化后测试套件 |
| **P6: 导出与执行** | 第 6 天 | 导出 Pytest 脚本 + 运行 | 分析测试结果 + 记录通过的用例与发现的缺陷 | 可运行测试脚本 + 缺陷报告 |

### 5.2 手工测试流程 (对照)

采用双人并行协作模式：两人各自独立设计测试用例，完成后对比合并。

| 阶段 | 时间 | 测试员 A | 测试员 B | 产出 |
|------|------|---------|---------|------|
| **需求分析** | 第 1 天 | 阅读7条需求 + 识别风险 | 阅读7条需求 + 识别风险 | 各自的风险分析草稿 → 对比合并 |
| **黑盒设计** | 第 2-5 天 | 手工设计 TS-BB-001~004 (4套件) | 手工设计 TS-BB-005~007 + TS-WB-001~004 (7套件) | 各自的用例设计 → 交叉审查 |
| **白盒设计** | 第 5-7 天 | 代码审查 + 路径分析 + 状态建模 | 代码审查 + 路径分析 + 状态建模 | 各自的白盒用例 → 对比覆盖率 |
| **脚本编写** | 第 7-9 天 | 编写 Pytest 脚本 (黑盒部分) | 编写 Pytest 脚本 (白盒部分) | 可执行测试脚本 |
| **执行对比** | 第 9-10 天 | 运行测试 + 记录结果 | 运行测试 + 记录结果 | 两份独立报告 → 对比合并缺陷列表 |

### 5.3 测试级别

| 级别 | 目标 | 工具 |
|------|------|------|
| **单元测试** | 验证单个验证函数 (validators.py) 的正确性 | Pytest |
| **API 集成测试** | 验证 API 端点的端到端行为，包括数据库状态变化 | Pytest + Flask test_client |
| **系统测试** | 验证完整业务流程 (注册→登录→创建项目→创建任务→分配→统计→删除) | Pytest |

### 5.4 质量门禁

| 门禁点 | 条件 |
|--------|------|
| G1 — 生成完成 | AI 生成的所有测试套件中每个技术至少产出 1 个用例 |
| G2 — 覆盖率 | High 风险模块路径覆盖率 >= 85% |
| G3 — 通过率 | 有效测试用例(非已知缺陷)通过率 >= 90% |
| G4 — 缺陷发现 | 自动生成的用例至少发现 3/5 个已知缺陷 |

## 7. 测试框架选择与理由

### 7.1 选型对比

| 框架 | 适用性 | 优势 | 劣势 |
|------|--------|------|------|
| **Pytest** | API 功能测试 | 简洁的 fixture 机制、参数化测试、丰富的断言 | 不支持浏览器 UI 测试 |
| Selenium | Web UI 测试 | 跨浏览器支持 | 被测系统是纯 API，无 UI 层 |
| JUnit | Java 应用测试 | Java 生态成熟 | 被测系统是 Python |

### 7.2 选择 Pytest 的理由

1. **语言一致性**: 被测系统 (Flask) 和测试框架 (Pytest) 均为 Python，无需跨语言桥接
2. **Flask 原生集成**: Flask 内置 `test_client()` 提供进程内 HTTP 测试，无需启动真实服务器
3. **Fixture 机制**: Pytest fixture 完美支持测试数据库的 setup/teardown，每个测试用例独立运行
4. **AI 工具集成**: AutoTestDesign v2.2 的 Pytest 导出器可直接生成 `flask_app/tests/test_generated.py`
5. **CI/CD 兼容**: Pytest 输出 JUnit XML 格式，可直接集成到 CI/CD 流水线
6. **轻量级**: 无需额外安装浏览器驱动或外部服务

### 7.3 测试框架配置
