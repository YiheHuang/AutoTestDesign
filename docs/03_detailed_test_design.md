# 详细测试设计与执行文档

项目名称：Task Management Platform  
选定模块：任务管理模块（REQ-005、REQ-006、REQ-007）

## 1. 测试对象

本次详细测试选择任务管理模块作为重点对象，覆盖以下 3 条需求。

| 需求 | 内容 | 风险等级 | 测试优先级 |
|------|------|----------|------------|
| REQ-005 | 任务管理 | Medium | Medium |
| REQ-006 | 任务分配 | Medium | Medium |
| REQ-007 | 任务统计 | Low | Low |

选择该模块的主要原因有两点。第一，该模块同时包含创建、更新、删除、分配、统计等多类行为，适合同时展示黑盒和白盒测试。第二，该模块存在若干已知需求偏差，便于观察自动化测试设计工具在真实场景中的有效性与局限。

## 2. 测试设计思路

本轮测试首先通过 AutoTestDesign 读取标准需求、需求-代码映射与风险分析结果，再针对 REQ-005 到 REQ-007 生成黑盒和白盒测试资产。随后保留原始自动导出的脚本，并进一步整理出人工校验后的自动脚本以及一份人工编写的对照脚本，用于比较三者差异。

### 2.1 黑盒测试设计

黑盒部分采用等价类划分、边界值分析和判定表 3 种技术。

#### 等价类划分

等价类划分主要用于任务标题、优先级、状态和负责人字段。

| 字段 | 有效类 | 无效类 |
|------|--------|--------|
| `title` | 非空、长度在允许范围内 | 空、超长 |
| `priority` | Low / Medium / High | 非法枚举 |
| `status` | todo / in_progress / done | 非法枚举 |
| `assignee` | 合法负责人输入 | 空值、未注册用户 |

#### 边界值分析

边界值分析主要围绕 `title` 长度和日期输入展开。

| 检查点 | 代表值 |
|--------|--------|
| 最小长度附近 | 1、2 |
| 最大长度附近 | 199、200、201 |
| 日期边界 | 过去日期 |

#### 判定表

判定表主要用于任务创建、任务分配和任务统计的条件组合。

| 需求 | 典型条件 |
|------|----------|
| REQ-005 | 项目是否存在、优先级是否合法 |
| REQ-006 | 负责人输入是否存在、是否满足分配条件 |
| REQ-007 | 项目是否存在、统计请求是否有效 |

### 2.2 白盒测试设计

白盒部分采用路径覆盖和状态转换两种技术。

#### 路径覆盖

路径覆盖主要针对以下代码路径。

| 路径 | 关注点 |
|------|--------|
| 任务创建路径 | 项目不存在、标题非法、创建成功 |
| 任务更新路径 | 任务不存在、更新成功、非法输入 |
| 任务删除路径 | 删除成功、删除已完成任务 |
| 任务详情路径 | 任务存在 / 不存在 |

#### 状态转换

状态转换主要围绕任务生命周期建模，例如创建任务、查看任务、更新任务、删除任务和查询统计等流程。这种设计方式可以覆盖单纯字段校验之外的过程行为。

## 3. 测试脚本组织

本轮共保留 3 份测试脚本。

| 文件 | 作用 |
|------|------|
| `test_scripts/test_generated.py` | 原始自动导出脚本 |
| `test_scripts/test_generated_refined.py` | 人工校验后的自动脚本 |
| `test_scripts/test_human.py` | 人工编写的对照脚本 |

其中，后两份脚本都保持了与原始自动脚本一致的基本结构，仍然按等价类划分、边界值分析、判定表、路径覆盖、状态转换组织，而不是仅保留零散示例。

从用例规模上看，各脚本的测试函数数量如下。

| 脚本 | 测试函数数 |
|------|------------|
| 原始自动脚本 | 44 |
| 人工校验后的自动脚本 | 32 |
| 人工编写脚本 | 27 |

## 4. 工具实现与执行方式

测试执行统一采用 Pytest 与 Flask `test_client()`。

运行命令如下：

```bash
python -m pytest test_scripts/test_generated.py -v --tb=short
python -m pytest test_scripts/test_generated_refined.py -v --tb=short
python -m pytest test_scripts/test_human.py -v --tb=short
```

这种方式具有以下优点：

1. 不依赖额外启动 HTTP 服务；
2. 可以直接在进程内调用 Flask 路由；
3. 便于对比不同脚本版本的执行结果。

## 6. 异常现象解释

### 6.1 REQ-005 路径覆盖率从 43.8% 到 100% 的原因

第一次生成 REQ-005 的路径覆盖结果时，工具显示关联行 73 行、覆盖行 32 行，覆盖率只有 **43.8%**。同时，结果中还提示有 2 个代码段未覆盖，分别是项目任务列表接口 `project_tasks_list()` 和单个任务详情接口 `task_detail()`。

从表面上看，这像是白盒测试生成没有覆盖完整代码路径。但进一步对照需求描述和代码后，我认为更主要的原因是 REQ-005 的原始需求写得不够清楚。原始描述更强调任务创建、更新、删除，以及 `title`、`priority`、`status` 等字段校验，而对“查询项目下任务列表”和“查询单个任务详情”这类只读路径表达不足。这样一来，工具在生成路径覆盖用例时，会优先围绕需求中说得更明确的写操作路径展开，而没有把列表和详情接口作为同等重要的覆盖目标。

![REQ-005 原始路径覆盖结果](assets/req005_coverage_438.png)

这里也反映出白盒覆盖结果不能只看最终百分比，还要回到“需求-代码映射”本身检查原因。REQ-005 映射到的任务路由范围比较大，覆盖率又是按代码行统计的；如果需求没有把某些行为说清楚，即使这些代码已经被映射进来，生成出的用例也可能不会主动覆盖它们。因此，43.8% 不是简单说明代码无法覆盖，而是暴露了需求描述和覆盖目标之间的不一致。

为了验证这一判断，我们补充完善了 REQ-005 的需求描述，把任务列表查询和任务详情查询也明确写入该需求的行为范围。随后重新生成路径覆盖结果，关联行仍为 73 行，但覆盖行提升到 73 行，覆盖率变为 **100%**。这说明之前的低覆盖率并不是因为工具没有能力覆盖这些路径，而是因为需求描述没有把相关路径表达清楚，导致测试生成目标不完整。

![REQ-005 更新需求描述后的路径覆盖结果](assets/req005_coverage_100.jpg)

这个过程对本次实验有一个比较重要的启示：自动化测试设计的质量很依赖需求输入质量。对于像 REQ-005 这种包含多个接口行为的需求，不能只写“任务管理”或只强调写操作，还需要把创建、更新、删除、列表查询、详情查询等行为边界说明清楚。否则，工具生成的覆盖率可能偏低，但真正需要修改的未必是代码或工具，而是需求描述和测试目标本身。

### 6.2 REQ-007 黑盒测试中 EP/BVA 没有生成测试用例的原因

从 `run_results/REQ005_006_007` 目录中可以看到，REQ-007 有以下产物：

- `REQ-007判定表.csv`
- `REQ-007状态转换1.csv`
- `REQ-007状态转换2.csv`
- `REQ-007路径覆盖.png`

但没有 REQ-007 的等价类划分表和边界值分析表。这并不是导出遗漏，而是在生成阶段就没有形成有效的 EP/BVA 用例。

原因首先来自需求本身。当前 REQ-007 在 `data/sample_input/task_platform_reqs.csv` 中的定义非常简洁：

- `input_fields` 是空数组；
- `conditions` 是空数组；
- `expected_behaviors` 只有一条“存在 -> 返回统计结果”。

实际运行截图 `REQ-007标准需求生成.png` 也可以看到：

- 输入字段区域为空；
- 关联代码集中在 `project_stats()`；
- 条件与行为基本只有“存在 -> 返回”。

这与 REQ-007 的实际代码结构是一致的。`project_stats()` 本质上是 `target_app/flask_app/routes/projects.py` 中的一个只读统计接口。

其主要逻辑只有两层：

1. `project_id` 对应的项目是否存在；
2. 若存在，则聚合任务数据并返回统计结果。

这类需求非常适合：

- 判定表，因为存在“项目存在 / 不存在”的条件分支；
- 状态转换，因为可以建模为“请求统计 -> 校验项目 -> 返回统计结果”。

但它并不天然适合：

- 等价类划分，因为没有明确的输入字段集合和字段级有效/无效类；
- 边界值分析，因为没有可直接做边界切分的数值范围、长度范围或显式区间。

从工具实现上看，EP 和 BVA 生成器都是把完整的 `requirement_json` 发送给 LLM，然后期待 LLM 返回：

- `equivalence_classes`
- `boundary_analysis`
- `test_cases`

对应实现分别位于 `tool/src/test_design/black_box/equivalence_partition.py` 与 `tool/src/test_design/black_box/boundary_value.py`。

当需求本身没有输入字段、没有范围、没有边界信息时，LLM 往往只能稳定生成判定表或状态模型，而难以给出有意义的 EP/BVA `test_cases`。当前生成器对这种情况的处理是：

- 允许返回空 `test_cases`；
- 记录 warning；
- 页面最终表现为该技术下没有用例产出。

因此，REQ-007 没有生成 EP/BVA 用例，根本原因不是工具报错，而是：

1. 需求本身更像一个“存在性 + 聚合返回”的只读统计需求；
2. 没有明确输入字段、边界范围和字段约束；
3. 判定表和状态转换比 EP/BVA 更适合表达这类需求。

这也说明，当前工具对不同需求类型已经表现出一定的技术适配性。当需求不具备字段边界信息时，工具不会强行产出质量较差的 EP/BVA 用例，而是更容易在判定表和状态转换上产出结果。

## 7. 三类最终测试脚本的对比

为了更直观比较人工校验后的自动脚本与人工脚本，相关关键指标汇总如下。

| 维度 | `test_generated.py` | `test_generated_refined.py` | `test_human.py` |
|------|---------------------|-----------------------------|-----------------|
| 来源 | 自动生成 | 自动生成后人工校验 | 人工从头编写 |
| 测试函数数 | 44 | 32 | 27 |

通过对比可以得到两点结论。

第一，自动工具的主要价值体现在测试角度更充分，但是会有部分本身的bug。

第二，人工脚本天然可靠，但是测试角度不够丰富。

## 9. 不同模型生成性能对比

为了了解工具在不同模型下的运行差异，额外选取 REQ-005 任务管理需求进行了一个小规模对比实验。实验范围只包括 EP、BVA、DT 三种黑盒测试设计技术各生成一次，主要观察生成耗时和可解析用例数量，不直接评价用例正确性和缺陷发现能力。

| 模型 | 配置 | 总耗时 | 有效用例数 | EP | BVA | DT | 结果判断 |
|------|------|--------|------------|----|-----|----|----------|
| gpt-4o | yunwu.ai / 未启用 reasoning 参数 | 24.414s | 22 | 7.615s / 12 条 | 11.060s / 6 条 | 5.739s / 4 条 | 本轮最稳定 |
| deepseek-v4-flash | thinking disabled | 108.415s | 3 | 43.897s / 0 条 | 60.405s / 0 条 | 4.113s / 3 条 | DT 可用，EP/BVA 不稳定 |
| gemini-3.5-flash | free API | 70.940s | 14 | 16.245s / 8 条 | 18.400s / 6 条 | 36.295s / 0 条 | EP/BVA 可用，DT 不稳定 |

从结果看，gpt-4o 在本轮实验中速度和可解析产出都最好，三种技术都能返回当前工具可以识别的结构化结果。DeepSeek v4 flash 在 DT 阶段很快，但 EP 和 BVA 没有形成有效用例，说明当前流程对模型输出格式的一致性要求较高。Gemini 在 EP 和 BVA 阶段能够产出 14 条用例，但 DT 阶段没有形成有效结果，并且免费 API 仍存在配额限制风险，因此稳定性不如 gpt-4o。

这个结果对工具使用有一个比较直接的提示：如果目标是稳定完成一次完整的黑盒用例生成，当前配置下优先选择 gpt-4o 更合适。同时，DeepSeek 和 Gemini 在部分阶段也有可用产出，说明系统在模型选择上仍保留了一定灵活性，可以根据速度、成本和接口可用性选择合适的模型配置。

## 10. 系统泛化性分析

从本轮任务管理模块的实验来看，AutoTestDesign 并不是只针对 Task Management Platform 或某一个任务接口写死的脚本生成器。它真正依赖的是较通用的输入和处理流程：先把自然语言需求整理成结构化需求，再进行风险分析、黑盒测试设计、白盒代码映射，最后导出测试用例和可执行脚本。也就是说，系统关注的是“需求如何转化为测试设计”，而不是某个固定项目的接口名称或业务对象。

因此，只要其他项目也能提供相对清楚的需求描述和可读取的代码结构，本系统就可以迁移使用。例如学生管理系统中的学生注册、选课和成绩查询，电商系统中的商品管理、订单创建和库存扣减，图书馆系统中的借阅、归还和逾期处理，或者权限控制系统中的角色分配和访问校验，都可以按照类似方式生成标准需求、风险等级、黑盒分析表、白盒路径覆盖结果和测试脚本。从这一点看，本系统的泛化对象不是“任务管理”这个业务本身，而是具有输入字段、条件分支、状态变化或接口行为的软件项目。

在具体迁移时，系统可以根据需求特征自动选择或辅助选择合适的测试技术。字段校验类需求可以使用等价类划分和边界值分析，条件组合类需求可以使用判定表，有生命周期或流程变化的需求可以使用状态转换，涉及代码路径的需求可以进一步结合白盒路径覆盖。这样一来，不同项目虽然业务名称不同，但都可以被整理成“字段、条件、行为、代码路径”这些可测试元素。

另外，白盒部分通过“需求-代码映射”把需求与具体实现联系起来。如果其他项目的接口、服务函数和数据模型职责清晰，系统就可以继续生成路径覆盖结果，帮助测试人员从代码角度补充黑盒测试遗漏的路径。综合来看，本系统具有跨项目迁移价值，适合作为通用的测试设计初稿生成与辅助分析工具。

## 11. 结论

本次详细测试设计与执行可以得出以下结论。

1. AutoTestDesign 在测试设计阶段已经表现出明显优势。它能够较快产出黑盒分析表、白盒覆盖思路和大规模候选测试脚本，这一点是纯人工方式难以在短时间内达到的。

2. 自动生成脚本并不能完全跳过人工环节。原始自动导出脚本的问题较多，但经过一次规模不大的人工校验后，脚本质量有明显提升，缺陷发现能力也显著增强。

3. 从本轮实际结果看，更合理的工作方式不是“自动化替代人工”，而是“自动化生成初稿，人工做关键校验”。这一方式在时间成本和缺陷发现能力之间取得了更好的平衡。

4. 模型选择会直接影响工具的稳定性。以 REQ-005 的小规模实验看，gpt-4o 在速度和有效用例产出上更适合当前工具流程。

5. 系统具有跨项目泛化能力，并不局限于本次的 Task Management Platform。只要其他项目能够提供清楚的需求描述和相对可映射的代码结构，工具就可以迁移生成风险分析、测试设计和脚本初稿；但对于抽象需求或复杂代码映射，仍需要人工校验和技术选择。
